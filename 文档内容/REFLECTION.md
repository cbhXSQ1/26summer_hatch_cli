# REFLECTION: Hatch 项目反思报告

---

## 一、哪些 Superpowers 技能发挥了最大作用，哪些"形式大于实质"？

writing-plans可能是最有用的吧毕竟基本的框架的开发都是根据plan来的。然后一些测试规约可能只对框架有作用，先写测试再写代码然后再过红绿测试可能就很形式化了，改一个上下文管理问题这种需要实际端到端跑一跑的和界面问题这种需要视觉处理之类的问题普通的测试完全没有用但是反而一个东西要想做得有用或者至少能用最多的问题都在端到端测试里面发现，尤其是在代码不是自己亲手写的情况下更是这样。
然后agent_log这种日志类的文件也很形式化，不太能够矫正agent的思路和方向，而且哪怕是用来记录开发过程用来移交新对话处理也不如直接让ai在当前对话窗口里把做的事写进文档里。

## 二、TDD 强制在 AI 协作下是阻碍还是放大器？

对于这种个人小玩意TDD在前面写框架的情境下非常有用，至少纯cli的整个整体是完全可以在TDD下完成的，后面的对于上下文取舍的大部分问题TDD没有起到一个很正面的作用，应该只能说保证了ai不会把原本的代码逻辑改报废掉。
总的来说TDD强制在ai协作下相当适合前期的工作，搭配paln写出的test可以有效矫正思路。后面微调测试的时候就需要自己去掰扯定位了，也就是说TDD适合从无到有，但是从一到二的改进是没有正向收益的。
此外TDD驱动改进代码似乎在名义上只会改进新写的地方，但是整体代码无法优化，这可能恰恰是出现性能等问题的地方。

## 三、subagent 驱动的智能体工作流能自主运行多久而不偏离主题？

在最开始按照Plan开发的过程中，task完全不需要人工介入，只是我让它一个一个极小的task进行(循环链路里的每部分算一个大章节，每一个章节里比较独立的逻辑部分算一个task)这样我可以实时审阅它的想法以免出现偏差，在这种情况下，可能真的不需要人工介入。
在后期修理Bug时，需要频繁的人工介入，基本一次修理需要纠正一次，还有在半路就看到思路偏差的情况。我认为这可能有一个ds没有视觉能力和操控tui进行测试的能力的因素。

## 四、什么样的 task 颗粒度最优？

从逻辑上我感觉目前应用的task划分方式是比较优的，具体实验的话我只能说跨项目对比吧，这个要比之前按照一整个超级大项目直接写的方式好多了，而且也没法再细化。旁边那个web开发的项目细化了一点，但是没有到这个程度，就有点奇怪的bug无法一步搭起框架了。

## 五、SPEC / PLAN 质量如何影响实现质量？

规约质量对实现质量的影响，应该全部发生在冷启动验证阶段——一个陌生的 Claude 只拿 SPEC + PLAN 实现 T0.1–T1.1，然后让他去看模糊的规约。

SPEC 最初把 mypy 类型错误的 dataclass 命名为 `TypeError`，与 Python 内置异常同名。Claude 实现到一半停下来询问，因为 shadowing 内置异常会导致模块内 `except TypeError` 失效、linter 报 Redeclared。最终整个模型层、类型注解、测试类名全部重命名。这个漏洞的发现绝对性地提高了实现质量。我认为根本原因是在撰写规约方案时对于涉及的其他方面考虑不足，属于llm的痼疾。

PLAN T0.2 验证步骤只写了 `make test`，而 Windows 原生没有 make。Claude 验证时卡住，修订后 PLAN 补充了 `python -m pytest` / `python -m build` 的 Windows 替代命令。

看到规约的最重要的问题在于避免缺失。错误会被实现者报出来，缺失极可能会让人凭猜测继续。随意可以认为文档的质量检验方式是文档的详细程度。

## 六、你最有效的 prompt / context 策略是什么？为什么有效？

最有效的一套是让它先给我解释清楚要干什么，发现了什么问题，然后给出方案，然后再操作代码。这样我至少能看懂他想要干什么过程不是黑箱了。

## 七、凭据与分发这两条工程要求，迫使你想清楚了哪些原本会忽略的问题？

凭据要求迫使我做的第一件事是想清楚会出现什么样的泄漏情况：攻击者拿到日志文件 → 无泄露；拿到源码仓库（含 git 历史）→ 无泄露；拿到本机访问权限 → 受操作系统凭据管理器保护。然后采取相应的举措——keyring 存储（service_name = `hatch/<provider>`）、日志与终端永不出现明文、状态查看只显示 `****` + 末 4 位、`.env` 仅作后备并明示其明文风险、`.gitignore` 双保险。多供应商独立存储这一点也来自建模：每个 provider 的 key 分开存，一个泄露不影响其他。

分发要求让这个项目从原本的个人项目变成一个要有基础泛用性的项目。它暴露的问题我在看文档时没想到：Windows 用户没有 make，Makefile 是给 CI 的，本地要写清 `python -m pytest` 替代命令；安装依赖不是 `pip install` 一句话，还要处理 `.[dev]` 与 `-e .` 的区别；CI 必须真能复现本地环境（这就要求 `.gitlab-ci.yml` 补上了 `python:3.11` 镜像声明，否则 runner 默认环境连 Python 都没有）；key 在目标机器上如何配置要写进 README 而不是靠口头交代。
总的来说，凭据要求回答"泄露了会怎样"，分发要求回答"别人能不能照文档跑起来"——这两个问题都是单人开发时最容易被自己豁免的。

## 八、如果重做你会改变什么？

把上下文规约要求这个最基础的但是最难返工的东西更加细化，然后提前约定好要做什么样的UI，在实际过程中这两点是后期调整的重点和错误频发之处。然后还要调整一下task划分，然后再研究一下上下文管理，当前存在的问题是缓存命中率低，上下文污染很严重，这是上下文管理的重大灾难。

## 九、你对 Superpowers 这套方法论的批判

superpowers对于项目的大方向是可以从无到有的，但是"流程纪律能守住 AI 协作的质量"这样的一个假设的问题是，流程纪律不能涉及到方方面面，甚至说最完善的纪律是一个完全写完的项目。就必须要跑一堆端到端测试，这其实额外增加了负荷。
而且纪律规约等文档也是llm自己写的，不全面的地方实在太多。哪怕自己审稿也会因为没有完整的思考链路而丢失很多东西。
还有TDD有点冗余，开发过程里没看到有什么测试没过，极有可能测试是一个接近于摆设的东西。
不过目前看来如果全程使用agent代工，这套文档体系是必不可少且没有相同地位的东西可取代的。还没看到有什么可改进的方法。
